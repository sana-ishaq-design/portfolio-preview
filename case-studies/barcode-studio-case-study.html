A Utility That Stays in the Workflow

Designing a compact browser utility that makes barcode creation easier to understand, while preparing clear specifications for development.

Barcode Studio brings QR and linear barcode generation into a browser popup. I designed its user experience and developer handoff, working with developer @zfhassaan.

Designing With
Assumptions in View

The challenge was to support a small, time-sensitive task without making the interface feel like another complex tool. The documented competitive review considered web barcode tools, TEC-IT/desktop software, Chrome extensions and design tools such as Canva.

Context switching, unclear privacy communication and unnecessary complexity informed the design direction. These observations belong to that documented comparison scope; they do not establish that every competing product shares those limitations.

Stay close to the task

A toolbar popup offered a way to create an asset alongside the user's current browser workflow, without requiring a separate product workspace.

Different needs, one utility

The intended audiences included developers and operations teams creating identifiers, marketers preparing assets, and people encoding sensitive information. These are design audiences, not validated research personas.

Five assumptions.
Still to be tested.

No prior user research was documented at project start. The following assumptions guided the work and were not formally validated.

  1. Task completion in under 30 seconds.
  2. Users generate one format at a time.
  3. Batch export is a secondary use case.
  4. Users prefer automatic theme detection.
  5. Privacy messaging improves completion.

Under 30 seconds was a design target, not an achieved or measured completion result.

From Input
to Usable Output

The Create experience separates choosing a barcode type, entering content and checking a live preview. Each step has a distinct purpose, so a compact surface can still communicate a clear sequence.

Make the choices visible

The supplied designs show a symbology dropdown alongside quick choices. The intention was to expose familiar formats while keeping the main control compact. This is not evidence of a dropdown-free shipped interaction.

Separate input from output

Labels and guidance explain what to enter; a distinct preview lets the user inspect the result before continuing to Export. The flow supports correction before download rather than hiding output until the end.

Supplied design artifacts. The inspected implementation uses a symbology dropdown and includes format-specific guidance; its exact equivalence to these designs or the installed store package is not established.

Export Without
Unnecessary Detours

Single and batch export share one destination. The primary task stays visible, while batch input and ZIP output remain discoverable on the same tab. This balances a focused first use with repeat-work needs.

Supplied export designs use format tiles, including PDF. The inspected implementation uses a dropdown and supports PNG, JPEG, WebP and SVG. PDF export is not confirmed as shipped functionality.

A default, not another decision

PNG is the initial export default in the inspected implementation; a saved preference can be restored. This differs from the supplied tile-based presentation and does not establish a release chronology.

Keep batch work in context

The design places file import and batch export below the single-export controls. The source supports .txt/.csv input and ZIP output; the visual hierarchy treats batch work as secondary, an assumption still needing validation.

Trust, Preferences
& Implementation

Auto, Light and Dark controls sit in the product header in the supplied screens and inspected source. In the inspected implementation, Auto follows system preference and a manual choice is retained locally.

Supplied About design variants. Their styling differs from the decisions PDF and available implementation; they are not a verified before-and-after release comparison.

Privacy at the point of use

Designed around local barcode generation, with clear privacy messaging at the point of use. The inspected implementation generates locally and stores inputs and preferences in the browser's local extension storage.

This review did not independently verify all runtime network behavior. Absolute zero-network-activity claims are not established. Store disclosure and its linked policy remain unresolved; neither is proof of payload transmission.

Information without a new workspace

The About overlay groups privacy information, shortcut guidance, developer attribution and GitHub feedback links. Development is credited to @zfhassaan; the case study separately documents my UX design and handoff contribution.

Specifications that carry the design forward

Named colour roles, typography examples and annotated dimensions make the design decisions tangible for development. These are supplied design specifications, not a claim that every token or type choice was implemented unchanged.

The annotated handoff documents a 340×740 design frame. The inspected source uses different width limits and vertical scrolling; the frame is not a verified shipped popup size.

What Shipped,
What Remains to Validate

Documented product availability

The published listing reviewed for this case study documents QR and linear barcode generation, PNG/JPEG/WebP/SVG export, batch generation, Wi-Fi QR options and light/dark modes. These are documented product capabilities, not measured UX outcomes or a claim that I designed every current feature.

Clear limits to the evidence

The work delivered a documented creation/export flow, light and dark design treatments, and developer handoff. Usability improvements remain design intentions rather than measured results.

There is no verified 30-second completion result. All five assumptions remain untested in the project evidence. Release chronology is unresolved, and the inspected build is not confirmed identical to the installed store package.

Future validation should examine format selection, privacy-message comprehension and single-versus-batch use. The original proposal for three exploratory sessions is a future plan, not research already conducted. Error guidance and batch feedback also need version-aware evaluation: current source includes validation beyond the supplied screens.

Reflection

Designing a constrained utility makes hierarchy matter at every step: what to choose, what to enter, what to check and what to save. Clear handoff makes that reasoning available to the developer, while keeping design intention distinct from implementation and measured performance.
